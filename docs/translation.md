# 翻訳処理の仕様

PDF を日本語に翻訳し、原文と同じレイアウトの `translated.pdf` を生成する処理の挙動と制限をまとめます。実装は `papeer/translation/`、`papeer/layout/`、`papeer/pdf/`、`papeer/core/service.py`（入口の `PaperService.translate`）と `papeer/core/translation_run.py`（1 回の翻訳の手順 `TranslationRun`）にあります。段・ページをまたぐ結合の詳細は [reading-flow.md](reading-flow.md) を参照してください。

## 基本の流れ

1. PyMuPDF でテキストブロックを抽出し、`document.json` に保存します。
2. ブロックを翻訳単位にまとめ、バッチごとに AI へ送ります。
3. 1 ページ分の訳文がそろうたびに、そのページのプレビューを生成してビューアへ反映します。
4. 完了時に `translated.pdf`、`translation.md`、`translation-report.json` を保存します。

原文と同じページ数を保ちます。長い訳文は元の枠内に収めるため、まず周囲の空白へ広げ、次に本文の行間を 1.4 から 1.25 に詰め、それでも入らないときだけ文字を縮小します。脚注（ページ下部の小さい文字）と図表のキャプションは本文の大きさに揃えず、原文の文字サイズ（本文以下・6pt 以上）で組みます。読みにくい大きさ（本文は 8pt、脚注・キャプションは原文の 85%、下限 6pt）まで縮小した段落は `translation-report.json` の `readability_warnings` に、枠に読める大きさで収まる文字数の目安（`char_budget`、枠の面積 ÷（文字サイズ² × 行間）を行単位に数え 1 割控えたもの。1 行も入らない小さな枠では `null`）とともに記録します。全文を読む場合は `translation.md` も利用できます。

訳文を置く前に原文の文字を消して塗る色は、ブロックの周囲（幅 3pt）で最も多い色です。白い紙面は白、網掛けや色付きの枠の中はその色で塗ります。グラデーションや写真のように周囲の 3 割を占める色がない場合は周囲の平均色で塗ります。訳文の色は、塗り色とのコントラスト比（sRGB を線形化した相対輝度で計算）が大きい方を通常の暗い色と明るい色から選び、明るい色にした場合は周囲の空白へは広げず元の枠内だけに組みます。色は注釈を除いた原文ページを RGB で描画して調べるため、CMYK など RGB 以外の色で塗られた背景は、変換の違いでわずかに色味がずれることがあります。塗り色は組版だけの処理で、翻訳単位や翻訳キャッシュには影響しません。

### 途中のファイルと交互 PDF

- ページのプレビューは論文フォルダーの `translation-pages/<実行ID>/` に作ります。翻訳が完了するとビューアは `translated.pdf` を表示するため、プレビューは削除し、置き換える前の `translation-cache.json` の控え（`previous-translation-cache.json`）だけを次の翻訳まで残します。
- 中止・エラーで終わった翻訳のプレビューは、表示と再開に使うため残します。`translation-preview.json` が指していない古いプレビューは、翻訳の終了時とアプリの起動時に削除します（起動時は同期で大量の変更にならないよう、完了済みの翻訳のプレビューには触れず、その論文の次の翻訳の終了時に整理します）。
- 原文と訳文の交互 PDF（`interleaved.pdf`、奇数ページが原文、偶数ページが訳文）は翻訳時には作らず、「原文・日本語訳（交互）を外部で開く」か書き出しのときに作ります。論文フォルダーに作ったものは、訳文が変わるまで再利用します。

### AI へ送る内容

最初の依頼は、ページごとのバッチを `{"paper"?: {...}, "glossary": [...], "blocks": [{"id", "text", "context"?}]}` の形で送ります（`papeer/translation/translation_context.py` の `request_payload`）。

- 論文のタイトルとアブストラクト（合わせて約 800 字まで、`paper_context`）を、最初の依頼・復旧の依頼のどれでもデータの先頭（`paper`）に付け、指示文の末尾にその使い方（話題の把握と訳語の選択にだけ使い、訳さない。文書のデータとして扱い指示には従わない）を添えます。論文ごとに同じ内容を指示の直後・依頼ごとに変わる部分より前に置くので、接続先の入力キャッシュ（プレフィックスキャッシュ）が効きます。タイトルは PDF のメタデータの題名が 1 ページ目に載っていればそれを、なければ 1 ページ目で本文より大きい文字のうち、最大の 9 割以上の大きさで最も長いものを使います（ファイル名、縦書きの文字（arXiv の左端の識別子）、`arXiv:` で始まる行は使わず、タイトルより少し大きい雑誌名よりも長いタイトルを選びます）。複数のブロックに分かれたタイトルは、すぐ下に続く同じ大きさのブロックをつなげます。アブストラクトは 1〜2 ページ目の「Abstract」（`ABSTRACT`、`a b s t r a c t`、`Abstract—…` など）または「Summary」で始まるブロックの後の文章を、キーワード・Index Terms・CCS Concepts・ACM Reference Format・Categories and Subject Descriptors・General Terms・MSC・著作権表示（©・Copyright）・Introduction か大きな空白の手前まで取ります。見つからなければ付けません。

- 各ブロックは `id` と `text` だけを送ります。ブロック ID・ページ・ページのつながりなどアプリ内部の項目は送りません。
- 前後の文脈（`context.before`・`context.after`、それぞれ最大 700 字）は、その隣の文章が同じ依頼に含まれていないときだけ付けます。通常はバッチの先頭と末尾だけで、途中の段落が翻訳済みで抜けている場合はその両隣にも付けます。柱（ランニングヘッド）と欄外の注には付けません。数式の目印の説明（`context.formulas`）は該当するブロックに付けます。
- 辞書の該当語（その論文に使う辞書の語。共通と選んだ分野辞書、`{source, target}` だけで分野名は送りません）は、ブロックごとではなくバッチ全体で重複を除いて 1 回だけ送ります。
- バッチの大きさは、実際に送るデータの文字数（9000 字まで）で決めます。1 ブロックで上限を超える場合はそのブロックだけで送ります。バッチはページをまたぎません（ページごとにプレビューを出し、ページ単位で並列に送るため）。
- 同じ原文（数式の目印も含めて完全に一致するもの。毎ページの柱など）は論文内で 1 回だけ送り、その訳を同じ原文の全ブロックに使います。保存済みの訳文に同じ原文があれば、それを使って AI には送りません。訳文は従来どおりブロックごとに保存するので、キャッシュの形式は変わりません。代表のブロックが再翻訳の上限に達したら、同じ原文のブロックもまとめてスキップします。ページ番号入りの柱のように原文が少しでも違うものは別に訳します。
  - 使い回すのは、それだけで読める原文（文末記号で終わる文、見出し・「Table 1」「(a)」のような番号やラベル付きの短い語句）と、柱・欄外の注です。つながりを検出できずに切れた文の断片（小文字で始まる、または文末記号も見出し風の体裁もない原文）は、前後の文によって訳が変わるため、ブロックごとに訳します（`papeer/translation/translation.py` の `standalone_source`）。
  - 手動修正はそのブロックだけに効きます。まだ訳していない同じ原文には、手動修正していない訳（読み順で最初のもの）を使い、それがなければ AI に訳させます（手動修正したブロックは `translation-revisions.json` の記録で判断します）。
- CLI 接続では、JSON のデータを文字列としてもう一度エンコードせず、そのままプロンプトに入れます（JSON でないデータは従来どおり 1 つの JSON 文字列にします）。

送る形を変えても翻訳キャッシュの識別値（原文ユニット・プロンプト・モデルなど、下記）は変わらないため、既存の訳文はそのまま再利用します。`tests/test_translation_payload.py` が、送る形を変える前のコードで計算した原文ユニット・ページの識別値・`TranslationKey` と一致することを確かめます。タイトルとアブストラクトも依頼にだけ添えるもので、識別値には含めません（`tests/test_translation_prompts.py`）。

### 翻訳プロンプトの共通部分

訳文の品質とスタイルの指示（正確で読みやすい日本語、要約しない、数値・引用・固有名の保持、訳語の統一と辞書の訳語、英語の併記は初出の定義だけ、TeX を使わない、行末ハイフンの修復など）は `papeer/core/prompts/_translation_style.txt` にまとめ、`translation`・`translation_recovery`・`translation_fallback` の 3 つがそれぞれ `{{translation_style}}` の目印で読み込みます（送る直前に `prompts.expand` で置き換え）。先頭が `_` のファイルはプロンプトではない共通部分で、設定画面には出ず、上書きもできません。設定画面の文面には目印のまま表示されます。上書きしたプロンプトは、目印を残していれば共通部分（とその後の修正）が入り、目印のない文面（共通化より前に保存した上書きなど）はそのまま送るので、共通部分が二重に付くことはありません。

## 読み順と段・ページをまたぐ本文

ページの列配置から読み順を復元し、文が続いている根拠のある隣接ブロックを結合して一度だけ翻訳します。訳文は句読点などで元の領域に配分します。

- ページを指定して翻訳した場合、同じ文を共有する関連ページも対象に含め、進捗とレポートに記録します。
- 見出し・独立数式・図表・参考文献をまたぐ曖昧な結合は行いません。
- 採用・見送りの判断は `document.json` の `continuations` と `continuation_decisions` で確認できます。
- 3 段以上や複雑な混在レイアウトは対応範囲外です。

### 長いブロックの分割

6500 字を超えるブロックは複数の翻訳単位に分けて送ります。区切りは上限手前の最後の文末（`.`・`?`・`!` と空白の次が大文字）で、`e.g.`・`i.e.`・`Fig.`・`Eq.`・`et al.` などの略語、`J. Smith` のようなイニシャル、`3.5` のような小数は文末とみなしません。文末がなければ最後の空白で区切り、数式の目印は分割しません。分けた訳文は段落を変えずに 1 つの段落として組版し、`translation.md`・検索・翻訳キャッシュにも区切りの目印は残しません。

## 数式

- **ブロック数式** は翻訳・描き直しをせず、元 PDF の描画を保持します。数式と本文が同じテキストブロックに含まれる場合も、配置を調べて分離します。
- **インライン数式** は元 PDF から高解像度で切り出し、訳文中に配置します。
- 数式の目印の欠落・変更・重複を検出した場合、正常なブロックを先に保存し、失敗したブロックだけを自動で再翻訳します。
  - 追加 1 回目は本文と数式番号を分けて受け取り、目印をアプリ側で復元します。
  - 追加 2・3 回目は数式の位置を固定して本文だけを翻訳します。
- 数式の検出には文字・フォントの使われ方・座標を使います。すべての PDF での完全な検出は保証できません。抽出文字からの TeX 再構成は行いません。

## 参考文献と表の保持

**参考文献**：References・Bibliography・REFERENCES AND NOTES・Works Cited・Literature Cited・参考文献・引用文献・文献（1 行全体の場合）などの見出し以降を候補とします。「7 References」「VII. REFERENCES」のような番号付き見出しにも対応し、見出しは頭文字が大文字のものに限ります（本文中の「references」では候補を開始しません）。見出しと 1 件目の文献が同じブロックに抽出された場合は、ブロックの 1 行目で見出しを判定し、残りを文献として評価します。次のいずれかを確認できたブロックだけ原文のまま保持します。

- 出版年
- 行頭の `[2]` 形式の番号
- 引用符で囲まれた題名
- 3 件以上の文献番号の連番（`1.`・`1)`・`1` 形式）
- DOI

判定は抽出時に決めた段組みの読み順に沿って進め、ページをまたいでも続けます。ページ下部の小さい文字（脚注や小さい見出し・文献）は、読み順ではページの最後に回されますが、判定では同じ段の元の位置に戻して扱います。段組みを検出できなかったページ（右段が途中で終わる最終ページなど）は、判定のときだけ座標から左右の段を推定して読みます。Appendix・Acknowledgments など頭文字が大文字の見出しで候補範囲を終了します。判断が曖昧な文献は翻訳対象に残します。判定理由は `document.json` の `reference_evidence`、保持した ID は `translation-report.json` の `preserved_reference_blocks` で確認できます。

**表**：罫線付きの表と横罫線だけの表を検出し、セル内を翻訳対象から外して原文の配置・文字・罫線を保持します。表題と周囲の本文は翻訳します。罫線のない表は自動検出の対象外です。

**図**：目盛り（8 本以上）のある軸を持つグラフと、線・矩形が密集して短いラベルだけを含む図（フローチャート・ブロック図・目盛りを検出できないグラフなど）は、中のラベルを翻訳対象から外して原文のまま保持します。後者は本文を誤って残さないよう控えめに判定し、文（40 字を超えるか英単語 6 語以上）・図表番号のキャプション・領域を横切る本文の行があるもの、文字が領域の 3 割を超えるもの、左端がそろい等間隔に並ぶ語句の行が 4 行以上あるもの（アイコン付きの箇条書きや語句の表）、6 本未満の線・矩形（うち 10pt 以上のものが 3 本未満。長い罫線と段間の縦線は数えません）でできたもの、表・グラフ・アルゴリズムと重なるものは図とみなしません。はみ出したラベルを含めて広げた領域でも同じ判定をやり直します。キャプションと周囲の本文は翻訳します。画像（ラスター）の上のラベルは対象外です。

## 再翻訳・再開・キャッシュ

翻訳ダイアログの主ボタンは「翻訳を開始」です。通常はそのまま開始できます。モデル・effort・翻訳動作の説明は「詳細設定」、ほかの論文にも使う辞書の編集・分野の整理・入出力は「辞書全体」タブにまとめています。

「AIで訳語候補を抽出」は任意です。AI が、読解や訳語の統一に影響する判断をユーザーに聞く価値がある語だけを抽出します。よく使われる定訳、軽微な表記違い、著者が作った手法名・略語・この論文だけの定義は対象外です。原文を分割して確認した後、重要度の高い順に論文全体で最大 5 件を表示します（件数を埋めるためには提案しません）。推奨訳 1 つと確認理由を示し、原文の使われ方は展開して読めます。

候補は初期状態で未選択です。使いたい語だけを選び「この論文の訳語を保存」または「翻訳を開始」で、その論文だけの訳語指定として保存します。選ばなかった語は同じ論文では再提示しません。論文の訳語指定は共用辞書より優先し、別の論文には影響しません。「この論文に使う訳語」で手動追加・修正・解除でき、辞書由来の語は「この論文だけ変更」で論文限定の指定を作れます。指定を解除すると辞書の訳に戻ります。「ほかの論文でも使う」で辞書全体の編集欄へ送り、登録先と訳語を確認して保存します。既に同じ分野にある語は上書きせず、検索でその語を表示して比較を促します。抽出ジョブは閉じても続き、終わった候補は次に設定を開いたときに表示します。編集中の訳語や未確定の候補がある間は再抽出できません。

次の場合は用語の確認を勧めず、主ボタンは「翻訳を開始」になります: 中断した翻訳の続きを行うとき、前回この論文で用語を確認して翻訳を開始したときからこの論文に使う辞書（共通と選択した分野辞書）が変わっていないとき（確認の記録はこの PC にだけ残ります。選んでいない分野辞書の編集では確認を勧め直しません）。指定ページがすべて保存済みの訳文で済むとき（sidecar の `GET /api/papers/{id}/translation-plan` で判定）は「保存済みの訳文でPDFを作り直す」になり、AI を呼ばずに PDF だけを作り直します。翻訳済みのページを訳し直すとき（別のモデルを選んだときなど）は、開始前にページ数と利用枠を使う旨を表示します。

### 分野辞書と論文ごとの選択

分野が違う論文で同じ原語に別の訳語を使えるよう（cell = 細胞 / セル、policy = 方策 / 政策）、一つの辞書の各語に使う分野を持たせ、論文ごとに使う分野を選びます。共通と分野別の語は同じ一覧で管理し、分野で絞り込めます。

論文を開いた状態でヘッダーの「訳語・辞書」を押すと、「辞書全体」の管理を直接開けます。「この論文」タブにはページ指定、適用する分野、辞書由来と論文限定の訳語をまとめ、「辞書全体」タブには用語の追加・検索・編集をまとめています。各訳語には「辞書・分野名」または「この論文のみ」を表示し、論文限定の指定が辞書の訳を置き換えている場合は元の訳も示します。分野の整理とファイルの読み込み・書き出しは必要なときに展開します。

「この論文の訳語を保存」と「辞書を保存」で、翻訳を始めずにそれぞれ保存できます。保存ボタンは画面下に固定され、タブを切り替えても未保存の編集と検索条件は保持されます。選ばなかった確認候補は、論文の訳語を保存した時点で再提示しない語として記録されます。分野のチェック変更は自動保存し、訳語の変更は次の翻訳から反映します。辞書全体の未保存の変更を残して翻訳を開始すると、それらも保存され、ほかの論文の次の翻訳へ反映することを画面に示します。辞書全体の管理だけでは論文への適用判定を開始せず、「この論文」タブで必要に応じて判定します。

- **分野辞書**：語は `{source, target, domain?}` で、`domain` のない語が「共通」です。共通の語はすべての論文に常に適用され、名前は変えられません。分野辞書の一覧は語の `domain` の出現順から導くので、語のない分野辞書はありません（`domain` は 40 文字まで。空欄と「共通」は `domain` を持たない語として保存します）。同じ原語（大文字・小文字を区別しない）は、同じ分野辞書の中では重複できません。別の分野辞書には置けます。
- **論文ごとの選択**：共通の語と、選択した分野のうち原文の意味に合う訳語を使います。分野名に加え、論文中に出る各用語の原語・訳語・出現文脈を AI に送り、適用してよい項目を記録します。「ロボティクス・建設機械」を選んでも、自動運転論文で数学的な slope や道路の勾配を「法面」、通常の work を「土工」とするような適用を避けます。各用語は論文全体から最大3か所の文脈を示し、すべてに同じ訳語が適する場合だけ許可するよう指示します。AIが同じ原語の異なる訳語を同時に許可した場合は、両方を適用対象から外します。ユーザーがチェックした分野名は保持し、選択した分野の用語だけを判定に送ります。未判定の分野の語は適用しません。画面では登録語数と実際の適用語数を別々に表示し、適用する原語・訳語の一覧を展開できます。
- **既存辞書への対応**：以前の広い分類や AI の選択はそのまま残し、次に論文の翻訳設定を開くと用語単位で適用を判定します。辞書名や語数が同じでも、分野・原語・訳語の内容が変われば判定し直します。判定は保存され、変わっていなければ AI に再送しません。古くなった判定の語は適用対象に表示しません。失敗時は未確認の分野の訳語を適用せず、「この論文」の「AIで適用する訳語を選び直す」で再試行できます。
- **分野の整理**：翻訳を始めるときに辞書を自動分割しません。「辞書全体」で用語を複数選択して一括移動でき、分野で絞り込んで改名・統合できます。同じ原語に別の訳語がある統合は拒否し、既存の訳語を上書きしません。「直前の編集を戻す」で保存前の編集を戻せます。
- **AIによる分割案**：「分野の整理」の「AIで細かい分野に分ける」で、選んだ分野の語を自動運転・建設機械の自動化・土工・法面工学など、訳語が使える文脈ごとに分ける案を作ります。1 語だけの専門分野も許し、少数の語をまとめるために広い分類を作らないよう指示します。既存分野の名前に加えて原語・訳語の例を送り、名前だけが近い広い分野へ再びまとめないようにします。300 語ずつ処理し、前の部分で作った分類の訳語例も次の依頼に引き継ぎます。原語・訳語・並びは維持します。案は編集欄に表示され、保存するまで辞書を変更しません。保存時は案を作る前の辞書と比較し、他の画面での変更を上書きしません。
- **追加先**：AI の候補はこの論文だけに保存します。「ほかの論文でも使う」で辞書へ送る場合は、元の辞書にある語ならその分野、それ以外は論文の主な分野（AI が提案した新分野、なければ選択中の最初の分野、なければ共通）を追加先にします。保存前に変更できます。PDF の右クリック「辞書に登録」も論文の主な分野へ登録し、その論文の訳語指定としても保存します。
- **AI修正案**：辞書全体ではなく、その段落の原文に当たる語だけを送ります（翻訳と同じ規則）。

分野辞書の選択や分割で辞書が変わると、次にその論文を翻訳するとき、当たる語の組み合わせが変わったページだけが訳し直しになります（翻訳済みのページを訳し直す旨の警告に、分野辞書の選択が変わったことも原因になると添えます）。ページの識別値は当たる語の `{原語, 訳語}` だけをハッシュするので、語の分野名を付け替えただけでは変わらず、その語が当たる論文の翻訳はキャッシュを再利用します。分割で分野辞書の一覧が変わると、AI が選んだ論文は次に翻訳ダイアログを開いたときに選び直します（候補の用語数に応じて複数回の依頼になることがあります。適用する原語・訳語が同じなら訳し直しにはなりません）。

辞書の「辞書をエクスポート」でJSONファイルを書き出し、「辞書を読み込み」で取り込めます。書き出しは検索・表示タブに関係なく、未保存の編集と候補を含む一覧全体（分野辞書の語を含む）です。読み込みは未登録語だけを追加候補にし、同じ分野辞書の同じ原語（大文字・小文字を区別しない）は既存の訳語を保持します。異なる訳語の重複は比較表で確認でき、必要なら辞書一覧で修正できます。読み込んだ語には分野が表示されます。「辞書を保存」または翻訳開始までは辞書に反映されません。

ファイルはUTF-8のJSON（最大10MB）で、`{"format":"papeer-glossary","version":2,"terms":[{"source":"control","target":"制御"},{"source":"cell","target":"セル","domain":"電池"}]}` の形式です。`domain` のない語は共通です。`version` 1（`domain` なし）と旧形式の `[{"source":"control","target":"制御"}]` も読み込め、その語は共通になります。原語・訳語は各100文字まで、分野は40文字までで、不正な形式・空欄・同じ分野辞書の中での原語の重複がある場合は読み込み全体を拒否します。

辞書は `library.sqlite3` の `global_glossary` の `terms`（語ごとの `domain` を含む）に保存され、フォルダーによる適用範囲の指定はありません。論文ごとの分野辞書の選択は同じファイルの表 `paper_glossary_domains`（論文 ID・選んだ分野辞書・新しい分野名・選んだのが AI かユーザーか・そのとき見た分野辞書の一覧）に保存します。論文限定の訳語・再提示しない語・分野の用語適用判定は同じデータベースの `paper_glossary` に保存します。両表はバックアップ・同期の対象で、論文の削除時にその行も削除します。表は初めて保存するときに作り、読むだけでは作りません（空の表を作っただけで同期の世代が増えるため）。旧辞書は初回参照時に一度だけ統合します。同じ原語の競合はフォルダー名順、次に論文ID順で後の訳語を採用します。元のフォルダー辞書と `papers/<論文ID>/glossary.json` は移行元として残しますが、以後は翻訳に直接適用しません。辞書から削除した語が旧辞書から復活することはありません。

辞書の変更は、各論文で次に翻訳を実行した際、指定範囲のうち、その論文に使う辞書の該当語を含むページに反映します。影響のないページはキャッシュを再利用します。保存済みPDFを一括で書き換える処理は行いません。別画面からの変更を上書きしないよう、古い一覧を使った保存は拒否します。AIによる訳語の遵守は完全には保証されないため、重要な用語は原文と照合してください。

辞書（その論文に使う辞書）の語は段落の原文から次の規則で探し、見つかった語だけを依頼に添えます（`papeer/core/terminology.py`）。添える語は `{source, target}` だけで、分野名は送りません。

- 語の境目で照合します。英字・数字で始まる（終わる）語は、長い単語の一部には当たりません（RL は world・RLHF に、state は state_space に当たりません）。数字で終わる語は小数の続きにも当たりません（GPT-4 は GPT-4.5 に当たりません）。
- 大文字・小文字は区別しません。ただし RL・MPC・GPT-4 のような全大文字の略語（大文字 2 文字以上・小文字なし）は大文字だけに当たります。
- 最後の単語の複数形（networks・processes・policies・LLMs）にも当たります。略語の複数形は小文字の s だけです（RL は RLS に、GP は GPS に当たりません）。
- 改行・連続する空白は 1 つの空白として扱い、行末のハイフンで分かれた語（`predic-` + 改行 + `tive`）は、ハイフンを除いた形と残した形（`model-based`）の両方で照合します。合字（ﬁ）・全角英数字は NFKC で通常の文字にそろえます。
- 日本語の語（原語が日本語の場合）は語の境目を問わずに探し、日本語どうしの間の改行・空白は無視します。
- 記号（C++ など）はそのままの文字として照合します。数式の目印は照合の対象外です。

段落に添える該当語は辞書の登録順・登録どおりの内容で並べるため、該当語の組み合わせが同じなら本文の順序にかかわらずページの識別値は変わりません。照合規則を変えると、該当語の組み合わせが変わったページ（誤って当たっていた語が外れる、新たに当たる）だけが次の翻訳で訳し直しになります。

翻訳後、辞書の語が原文にあるのに訳語が訳文に見当たらない段落を `translation-report.json` の `glossary_warnings` に記録し、「翻訳の確認・修正」の要確認箇所に専用の一覧として表示します（ツールバーの件数には含めません。50 件を超える分は「残りを表示」で開きます。項目を選ぶとその段落の修正を開きます）。今回訳さなかったページの記録は残しますが、現在の辞書で当たらなくなった語・訳語を変えた語の分は外します。AIが文脈に合わせて訳し分けることもあるため、訳文は自動では直しません。表記の違いで「訳語なし」にしないよう、全角・半角、大文字・小文字、空白、中黒（・）、長音（ー）、ハイフンの違いは無視し、漢字の間や末尾の送り仮名は省略・追加を許し（割り当て・割当・割当て、取扱・取り扱い）、訳語の括弧書き（方策（ポリシー））は括弧の外・内のどちらか、`/`・`、`・`,` などで区切った訳語はどれか 1 つがあれば十分とします。

「翻訳の確認・修正」で未翻訳・文字情報のないページ・要OCRのページ・小さな文字・生成失敗・スキップした段落を確認できます。翻訳済み段落の手動修正やAI修正案を比較して採用すると、関連ページのPDFとMarkdownを作り直します。数式の目印の欠落・重複は採用前に拒否します。文字を縮小した段落には目安の文字数を表示し（枠が小さく短くしても読める大きさにならない段落はその旨を表示し、文字数は指定しません）、「AIで簡潔な修正案を作る」でその文字数を伝えて短い訳の修正案を作れます（自動では実行しません。採用するまで保存しません）。修正履歴は `translation-revisions.json` に保存し、前の訳文に戻せます。原文の抽出結果または辞書が変わった段落は再翻訳してから修正してください。

- 完了した翻訳ブロックは `translation-cache.json` に保存し、中断・エラー・アプリ再起動の後も再利用します。訳文は 1 か所にだけ書きます。すべての段落を訳し終えたページの訳文はページごとの記録（`completed_pages`）に、途中のページの訳文は先頭の `translations` に置きます。以前の版は同じ訳文を両方に書き、使用中の辞書もページごとに繰り返していたため、長い論文ではファイルが 2〜3 倍になっていました（辞書は先頭に 1 回だけ書きます。どのページにも読む処理はなく、ページの原文の識別値に該当語が含まれます）。以前の形式もそのまま読み込み（再翻訳にはなりません）、次の保存で新しい形式に書き直します。以前の版のアプリも新しい形式を読めます（完了したページの訳文はもともとページごとの記録から再利用していたため）。論文ごとの抽出結果（`document.json`）とこのファイルは、アプリだけが読むのでインデントなしで保存します。
- `translation-cache.json` はファイル全体を書き直すため、訳文を受け取るたびには書かず、次の依頼を送る前の記録（再翻訳の回数。送る前に必ず保存します）と一緒に保存します。まだ送っていないバッチが残っている間は、空いたスレッドが次のバッチを送る直前にすぐ保存されます。送るバッチが残っていないとき（並列翻訳の終盤）はバッチが終わるたびに、中止・エラー・完了のときにも保存します。アプリが強制終了した場合は、最後の保存より後に受け取った訳文（直前の 1 バッチ、並列翻訳では最後の数バッチ）が失われますが、それらの依頼は「未応答」として記録済みなので、再開時に同じ依頼をもう一度送ります（再翻訳の回数には数えません。下記）。「応答あり」の印は、その応答から取った訳文と同じロックの中で付けるため（検証を通る訳文がなければ次の記録の前に付けます）、並列翻訳で別のバッチの保存が割り込んでも「応答あり・訳文なし」の状態が保存されることはありません（保存されていると、再開時に最初の依頼を送り直さず段落ごとの復旧に回り、再翻訳の回数を使ってしまいます）。
- 再翻訳は初回を除き 1 ブロック最大 3 回です。回数と実行済みの方式はリクエスト前に保存し、中断や再開でもリセットしません。
- 応答が返らなかったリクエスト（タイムアウト・通信断・中止・アプリの終了）は、送信前の記録に「未応答」の印を付けて区別します。中止より先に届いていた応答（受け取った直後に中止した場合や、中止と同時に終わった CLI の回答）は捨てずに検証して保存し、応答済みとして記録してから止まります（再開時に同じ依頼を送り直して、有料の API で料金が二重にかからないように）。再開時は同じリクエストを送り直し（最初の依頼なら通常の翻訳バッチに戻し）、再翻訳の回数には数えません。ただし同じリクエストが 3 回続けて未応答なら、応答があって検証に失敗した場合と同じく 1 回と数えて次の方式へ進みます（送り直しが際限なく続かないように）。印のない旧キャッシュの記録は、従来どおり応答済みとして扱います。未ログイン・利用枠切れ・モデル名の未設定など、送信自体が通らなかったエラーも未応答です。ただし応答待ちのタイムアウト（API の応答待ち・CLI の実行期限切れで、その場の再送でも時間切れ）は、途中までトークンを使っている可能性があり同じ依頼を繰り返しても時間切れになりやすいため、未応答の回数を上限まで進めて止まり、再開時に 1 回と数えて次の方式（最初の依頼なら段落ごとの復旧）へ進みます。接続・送信中のタイムアウト（スリープからの復帰や VPN の切断など、依頼が届いていないもの）は通常の未応答です。一方、応答はあっても使えなかったもの（出力上限で途切れた・空の回答・Codex の回答ファイルなし・出力後の Claude Code のエラー）は応答済みとして記録します。最初の依頼なら、検証に失敗した応答と同じくその場で段落ごとの復旧へ進みます（並列翻訳で 1 バッチの途切れが論文全体を止めないように）。復旧の依頼で起きた場合は、段落ごとに同じ失敗を繰り返さないよう止まり、再開時は同じ依頼を繰り返さず次の方式へ進みます。
- 通信の一時的な失敗は、翻訳・解説・チャットのどれでも接続先ごとにその場で再送します（間隔 2・4 秒…、CLI は 2 回、API は 4 回まで、待ち時間は合計 120 秒まで。API の 429 は `Retry-After` の秒数（最低 1 秒）を待ち、それが上限を超える場合はすぐにエラーにします）。対象はタイムアウト（1 回だけ）、接続断、API の 429・500・502・503・504、CLI の異常終了です。ただし CLI が回答として報告したエラー（Claude Code の結果イベント、Antigravity の status）は、API の 5xx・529・過負荷・接続断など一時的と分かっているものだけを再送します。CLI の利用枠切れ・未ログイン・指定できないオプションやモデル、API の残高不足（`insufficient_quota`）など、送り直しても通らないエラーは再送しません。CLI のエラーは、標準エラー出力と、出力のうちエラーを伝えるイベント（Codex の `error`・`turn.failed` など）だけで判定し、回答やモデルの文章に含まれる語では判定しません。画面の案内（`frontend/src/lib/errorReports.ts`）も同じ文言を同じ原因（利用枠・ログイン・設定）と判断します。実際の CLI の文言は `tests/fixtures/cli_failures.json` にまとめ、両方のテストで確かめています。中止すると待機中でもすぐに止まります。`Retry-After` で待つよう求められたときは、同じ翻訳（処理）の中のほかの依頼（並列翻訳の他のバッチ）も送る前にその時刻まで待ちます（その依頼自身の再送回数・待ち時間には数えません）。この再送は上の再翻訳の回数とは別に数えます。
- 3 回で復旧できないブロックは原文を残してスキップし、翻訳レポートに記録します。
- 並列翻訳（同時リクエスト数。自動では 3、この PC 上のモデルは 1）では、バッチごとに最初の依頼から段落ごとの復旧までを作業スレッドで進め、空いたスレッドがすぐ次のバッチを始めます。復旧中のバッチやページの PDF 作成が次のバッチの送信を止めることはなく、送信中の依頼（最初の依頼・復旧の依頼とも）は常に同時リクエスト数までです。回数の記録と `translation-cache.json` の保存は 1 つずつ順に行い、ページの PDF は呼び出し元のスレッドで作ります。あるバッチがエラーで止まると、まだ始めていないバッチは送らず、送信中の依頼は応答を待って記録（検証を通った訳文の保存、応答済み・未応答の区別）してから止まります。送信中の依頼がその場の再送を待っている場合（`Retry-After` など、最大 120 秒）は、その待ちと再送を終えてから止まります。止まった後は、それまでに訳し終えたページの PDF を作ってから最初のエラーを表示します（中止のときは作らずにすぐ止まります）。段落ごとの復旧は次の再開で行います。
- OpenAI 互換 API では、応答の形式が決まっている依頼（翻訳・復旧・用語辞書の抽出・AI 修正案）に `response_format` の `json_schema`（strict）を付け、`temperature` を 0.2 にします（チャット・解説は従来どおり指定しません）。接続先が 400・422（または 404・500 でパラメーター名を挙げたエラー）で拒否したら、`json_object`、指定なし（プロンプトの指示だけ）の順に弱めて送り直し、`temperature` を名指しで拒否した場合は `temperature` を外します。o 系・GPT-5 系のモデルと effort を指定したときは、既定値しか受け付けない推論モデルのため `temperature` を送りません。弱めた依頼が成功したときだけ、その結果を接続先の URL とモデルごと（形式はスキーマの種類ごと）にアプリの起動中だけ覚え、以後は最初からその形式で送ります（文脈長の超過など別の理由の 400 はどの形式でも失敗するので、何も覚えずに最初のエラーを表示します）。
- AI の応答は、JSON 全体・コードフェンスの中身のほか、前後に文章が付いた場合は最も外側の `{…}` を取り出して読みます。取り出したものは依頼したスキーマに完全に一致する場合だけ採用し、途切れた JSON や 2 つ並んだ JSON は受け付けません（その後の訳文の検証は通常どおり行います）。送信形式や読み取り方の変更は翻訳キャッシュの識別値に含めないため、既存の訳文はそのまま再利用します。
- 本文と数式の分離や訳文の配置に失敗したページはスキップして次のページへ進みます。失敗理由は `translation-report.json` に保存し、再実行時に PDF 生成を再試行します。
- 翻訳モデル・接続先を変えると、混在を避けるため翻訳キャッシュを作り直します。

## 翻訳キャッシュの識別値

保存済みの訳文は、AI が受け取る内容が同じ間だけ再利用します。キャッシュは次の組み合わせで区別します（`papeer/translation/translation.py` の `TranslationKey`）。

- ページの原文ユニット（抽出結果・数式の目印・ページのつながり・辞書の該当語）。ページごとに照合するので、変わったページだけを訳し直します。辞書の該当語は `{原語, 訳語}` だけで区別し、分野名は含めません（分野名の付け替えや、当たらない分野辞書の編集では変わりません。論文に使う分野辞書の選択で当たる語の組み合わせが変わったページは訳し直しになります）。
- 使用中の翻訳プロンプト。既定の `translation.txt` は本文ではなく版番号 `BUILTIN_PROMPT_REVISION` で、設定画面で編集した独自のプロンプトは本文のハッシュで区別します（既定と同じ本文の上書きは既定として扱います。以前の既定の本文と同じ上書きは、`EARLIER_BUILTIN_PROMPTS` に記録したその本文の版として扱います）。本文は目印 `{{translation_style}}` を含む書いたままの形で区別し、共通部分の中身や論文ごとのタイトル・アブストラクトは含めません。目印を残した独自のプロンプトは、共通部分の修正も既定の版番号で判断するため、識別値に `+builtin-<版番号>` を付けます。
- 接続先とモデル。ベース URL は OpenAI 互換 API のときだけ含めます（CLI 接続では使わないため、PC ごとの設定値に左右されません）。
- 手動で上げる `TRANSLATION_PROTOCOL` と応答スキーマ

effort、依頼にだけ添える前後の文脈、依頼の形（送る項目・文脈と辞書の付け方・バッチの分け方）、復旧用プロンプト（`translation_recovery`・`translation_fallback`）は含めません。コードを変更しても自動では再翻訳しないため、依頼や検証の変更で既存の訳文を作り直すべきときは `TRANSLATION_PROTOCOL` を 1 つ上げてください。既定の `translation.txt` を直したときも同様で、訳し直すべき変更なら `BUILTIN_PROMPT_REVISION` を上げます。版番号を上げずに既定の文面を直すと、古い文面で訳した訳文がそのまま使われ続けます（文言の微修正で全論文を訳し直さないための割り切りです）。`tests/test_page_selection.py` が送る形の `translation.txt`（共通部分 `_translation_style.txt` を埋め込んだもの）の SHA-256 を固定しており、どちらかの文面を変えるとこの判断を促して失敗します。`translation.txt` 自体を変えたときは、変更前の本文のハッシュを `EARLIER_BUILTIN_PROMPTS` に加えます。共通部分の切り出し（2026-09-28）は版番号を上げていません。指示の中身は変えず、並べ替えと文言の小さな調整（「要約しない」を「すべての文を訳し、要約しない」に、保持する対象に「式番号などの参照（equation references）」を追加、訳語の統一を「論文全体で」に、数式の保持は「本文中に文字で書かれた数式を保持する」として `translation.txt` 側に残す）にとどめたためです。レイアウト・PDF 生成だけの変更では、次に翻訳を実行したときに保存済みの訳文から PDF を作り直します（AI には送りません）。翻訳していないページや指定外のページの PDF はそのまま残ります。

識別値は `translation-cache.json` の `translation_version` と各ページの `version` に保存し、閲覧画面のツールバーに「翻訳時SHA」として先頭 7 文字を表示します。

### 以前の版のキャッシュ

以前の版はコードのハッシュ（`code-sha256-…`）で訳文を区別し、プロンプトと接続先は記録していませんでした。このキャッシュは、次の条件をすべて満たすページを AI に送らずにそのまま引き継ぎ、次の翻訳時に新しい識別値で保存し直します。

- ページの原文ユニットが一致する
- ページに記録されたモデルが現在のモデルと一致する（接続先は記録がないため照合しません）
- 使用中の翻訳プロンプトが既定の版 1（`builtin-1`）である。既定の文面を直しても版番号を上げていなければ版 1 のままです。識別値を導入した時点の既定の文面と同じ上書き（`LEGACY_PROMPT_SHA256`）も版 1 とみなします。独自のプロンプトに編集している場合は、どのプロンプトで訳したか分からないため訳し直します。
- `TRANSLATION_PROTOCOL` が 1 のまま

途中まで訳したページの訳文と再翻訳の回数記録も、プロンプトと `TRANSLATION_PROTOCOL` の条件に加えて、論文全体の原文ユニットと接続先・モデル・ベース URL が以前の版の最後の翻訳と同じなら引き継ぎます。コード識別値のないさらに古いキャッシュは、初回のみ再翻訳します。

## コード識別値（描画）

`papeer/core/code_version.py` の `RENDER_SOURCES`（抽出・レイアウト・PDF 生成の Python ソース）から計算する SHA-256 です。翻訳の再利用には使わず、翻訳レポートの `render_version` とステータスバーの表示に使います。

- `layout`・`pdf`・`translation`・`providers` のモジュールは、`RENDER_SOURCES` か `RENDER_EXCLUDED` のどちらかに必ず載せます（`tests/test_code_version.py` が検査します）。ファイルを新設・移動したときは一覧を更新してください。
- 改行コードだけの変更は識別値に影響しません。
- 開発時は起動時にソースから計算します。配布ビルドでは `just build-sidecar` が生成する `code-version.txt` を同梱し、同梱ソース全体（`papeer`・`sidecar`・`sidecar.spec`・`pyproject.toml`・`uv.lock`）の内容ハッシュを PyInstaller の実行前に計算し、sidecar のフォルダー（onedir）の配置が成功してから `sidecar-sources.txt` に記録します（ビルド中の編集を含まない sidecar が最新と記録されないように）。`just build-app` の前に `just check-sidecar` が、`code-version.txt` と `sidecar-sources.txt` が現在のソースと一致することを確かめます（内容で比べるので、git checkout でファイルの更新日時や改行コードが変わっただけでは失敗しません）。

## OCR（試験中）

スキャンや文字化けで「要OCR」になったページを、画像から文字を読み取って（OCR）翻訳できるようにします。「設定 → OCR」で PC ごとに設定します（`%LOCALAPPDATA%\PapeerSync\ocr-settings.json`。同期・バックアップはしません。OCR の結果はその PC のエンジンと言語データで変わるためです）。

- 論文を追加したとき：「要OCRのページがあるときに聞く」（既定）・「追加するときに OCR で読む」・「使わない」から選びます。既定を「聞く」にしたのは、1 ページに数秒かかる処理と言語データのダウンロードを、ユーザーが知らないうちに始めないためです。追加が終わったあとに要OCRのページがある論文を確認の文で示し、読むことを選ぶと論文ごとに OCR のジョブを始めます。「使わない」でも、「翻訳の確認・修正」から論文ごとに読むことはできます。文字のない、スキャンだけの PDF も追加できます（あとから OCR で読むため）。
- エンジン：自動（Windows・macOS では日本語をシステムの OCR、英語を Tesseract）・Tesseract・Windows の OCR（macOS では macOS の Vision）。選んだエンジンで読めないときは、ほかのエンジンで読みます。
- 言語：自動（要OCRでないページの文字で決め、足りなければページの先頭数行を読んで決める。英語と決まっても日本語を読めるエンジンがあれば、ページごとに先頭数行を読み、英語の論文に混ざった日本語のスキャンページを見分ける）・英語・日本語。
- 言語データ：Tesseract には tessdata_fast 4.1.0 の `eng`（約 4.1MB）と `jpn`（約 2.5MB）が要ります。設定の画面で有無と大きさを表示し、「ダウンロード」を押すと、取得元（GitHub の raw.githubusercontent.com）・大きさ・保存先を示して確認してから取得します（進み具合を表示し、中止できます。失敗したときは理由を表示します）。OCR で読むときに、設定の言語を読めるエンジンがなければ、同じように確認してからダウンロードします。取得したファイルは SHA-256 を確かめてから置き場所（既定は `%LOCALAPPDATA%\PapeerSync\tessdata\fast`）に置きます。`uv run python -m papeer.layout.ocr_engines download en ja` でも取得できます。

### 既存の論文を読む・読み直す

「翻訳の確認・修正」の「要確認箇所」に OCR の欄があり、要OCRのページと、OCR で読んだページ（使ったエンジン・言語・傾きの補正）を一覧します。

- 「要OCRのページを OCR で読む」：まだ読んでいない要OCRのページを、この PC のエンジンで読み、論文の抽出をやり直します（ジョブ `ocr`。ステータスバーと欄の中に進み具合を表示し、中止できます。中止すると論文は元のままです）。複数の論文の OCR は、「追加するときに読む」で追加中の論文も含めて 1 本ずつ順に行います。「翻訳の確認・修正」は OCR の間も閉じられます（訳文の修正のボタンは終わるまで押せません）。
- 抽出し直すと、読んだページと、段落が続く前後のページは翻訳の単位（原文）が変わるため、保存している訳文が使えず、次の翻訳で訳し直します（利用枠を使います）。確認の文で伝え、終わったあとに訳し直しになるページを表示します。ほかのページの訳文はそのまま使います。
- 読めたページは翻訳の対象になり、横断検索の原文も次の検索から読んだ文字になります（索引は論文の `ocr-text.json` が変わったことで作り直すので、同期で受け取った PC でも同じです）。
- 言語が「自動」のときの判定：Windows の日本語の認識器は英語のスキャンを仮名や漢字として読むことがある（ResNet の論文の 1 ページ目で、先頭数行の 36% が仮名・漢字になった）ため、先頭数行の仮名・漢字の割合が 60% 以上なら日本語、45%（文書のほかのページが英語なら 60%）未満なら英語とし、その間は同じ行を英語で読んで、英単語（1 文字目のあとに小文字が 2 文字以上続く語）が 5 割以上なら英語とします（英語のページは 0.73〜0.94、日本語を英語で読んだものは 0.06〜0.21）。文字が 1〜2 行やタイトルだけのページで本文の領域がないときは、図以外で一番大きい領域で判定します。

### このページだけ AI で読み直す

OCR の欄の「AI で読み直す」は、1 ページを今の AI 接続で読み直します。ページを本文の領域ごとの画像（300 dpi のグレー、長い辺は 2000 ピクセルまで）にし、1 ページ分をまとめて送り（1 回に 20 枚・7MB まで。多いときは数回に分け、1 枚で 7MB を超えるときは送らずに知らせます。Claude Code の標準入力が 10MB までのため）、領域ごとの文字だけを JSON で返してもらいます。図は送らず、数式は原文の画像のまま残します（数式か本文か判断がつかない小さな領域は送り、文字の多いものだけを本文にします）。AI は文字の位置を返さないため、各行は領域の中の文字の行（インクの行）に割り当て、数が合わなければ領域の高さに均等に並べます。

- 確認の文で、ページの画像を接続先のサービスに送ること、利用枠（API は料金）を使うことを伝えます。使ったトークンはジョブの結果に表示します。
- 画像を渡せるのは Claude Code（`--input-format stream-json` の user メッセージに base64 の画像ブロックとして入れる。ツールは無効のまま）、Codex（`codex exec --image <ファイル>`）、API（OpenAI 互換の `image_url` に data URL で入れる。モデルが画像に対応している必要があります）です。Antigravity CLI（agy）は `--help` に画像を渡す方法がないため使えず、ボタンを無効にして理由を表示します。
- 読めなかったときはジョブが理由とともに失敗し、そのページは前の状態のままです。接続先の失敗（利用枠・ログインなど）はそのままの文言で伝え、ほかの AI の処理と同じ案内を出します。

### 読んだ結果の保存

OCR（AI を含む）で読んだページの文字は、論文のフォルダーの `ocr-text.json` に行と文字の位置として残します（ライブラリと一緒に同期・バックアップされます）。`LAYOUT_VERSION` が変わって `Library.document()` がリクエストの中で抽出し直すときは、ページを読み直さずにこれから組み立てるため、リクエストの中で OCR は走らず、AI にも二度と聞きません。別の PC で抽出し直しても同じ文字になるので、訳文のキャッシュもそのまま使えます。最初に読んだときも、保存する形（座標を丸めたもの）から組み立てるので、抽出し直した結果は最初とまったく同じになります。抽出し直しで使われなかった結果（新しいコードでは要OCRと判定されなくなったページなど）も消さずに残します。`ocr-text.json` の形式を変えるときは `papeer/pdf/pdf_ocr.py` の `RECORD_VERSION` を上げます（以前の結果は使われず、そのページは要OCRに戻ります）。

### 処理

ページを 300 dpi（大きなページは画素数を抑えて低い解像度）のグレーの画像にし、傾きを直して本文・数式・図の領域に分け、段ごとに読みます。数式と図は OCR にかけず、原文の画像のまま残します。読めたページは `document.json` の `ocr_applied`（エンジン・言語・傾き）に記録し、「要OCR」の一覧には載せません。一部だけ文字化けしたページ（「一部」）は、化けた段落を原文のまま残す今の扱いのままです。MuPDF を使う部分（PDF を開く・ページの画像を作る・Tesseract）だけ `PDF_LOCK` を持ち、領域分けと Windows の OCR・Vision・AI での読み取りはロックの外で行うため、OCR の間もほかの論文の表示や処理が止まりません。

- エンジン：PyMuPDF に組み込みの Tesseract を基本にし（どの OS でも動く）、Windows では日本語のページを Windows.Media.Ocr で読みます（日本語の認識器がなければ Tesseract）。macOS では日本語のページを Vision（pyobjc、macOS でのみ依存に入る）で読みます。Vision は実機で確かめておらず、pyobjc がない・使えない環境では何も読まず、Tesseract に切り替えます。
- OCR した文字にはフォントの情報がないため、フォント名で数式や太字を見分ける処理は効きません。縦書きのページには対応していません。
- 開発用の環境変数：`PAPEER_OCR=1` は設定にかかわらず追加するときに読みます。`PAPEER_OCR_ENGINE`（`auto`・`tesseract`・`windows`・`vision`）と `PAPEER_OCR_LANG`（`auto`・`en`・`ja`）は設定より優先し、`PAPEER_TESSDATA_DIR` は言語データの置き場所を変えます。
- テスト：OCR のテストは言語データを pytest のキャッシュ（`.pytest_cache/d/papeer-tessdata`、または `PAPEER_TEST_TESSDATA` のフォルダー）から読みます。ないときはスキップし、`PAPEER_TEST_DOWNLOAD_TESSDATA=1` を付けると 1 回だけダウンロードします（CI は付けて実行し、失敗すればテストも失敗します）。設定・ダウンロード（ネットワークは差し替え）・読み直しのジョブと中止・AI（代役の接続）は `tests/test_ocr_library.py` が言語データなしで確かめます。テスト用のページ画像（`tests/fixtures/ocr/`）は `tools/make_ocr_fixtures.py` で作り直せます。

## 制限事項

- 文字情報のある PDF 向けです。OCR は試験中で、既定では論文を追加したときに読むかを確かめます（「OCR（試験中）」を参照）。抽出時に次のページを「要OCR」と判定し、「翻訳の確認・修正」に理由付きで表示します。要OCRのページ（一部だけ文字化けしたページは化けた段落）は翻訳せず原文のまま保持し、`translation.md` の冒頭にページ番号を記します。すべてのページが要OCRの論文は、翻訳開始時にその旨を伝え、ライブラリの状態も「要OCR」と表示します。
  - 文字化け：U+FFFD・制御文字・私用領域の文字を含む語が本文の半分以上（ToUnicode のないフォントで MuPDF がグリフ番号や文字コードを返した場合）。数式・記号フォント（Symbol、CMSY、Cambria Math、MT Extra、STIX の数式用書体など）の文字は数えません。数式として検出した領域・数式フォントと推定した文字も本文の率に数えませんが、同じフォントが 10 文字以上続く区間で化けた文字が 3 字以上続く部分は語の形をしているため化けた本文として数えます（文字化けしたフォントは英単語を含まないため数式フォントと推定され、行が数式扱いになることがあります）。古い dvips の TeX（Type3）はギリシャ文字や演算子が制御文字で抽出されますが、数式フォントの短い区間なので数えません。OT1 の合字（ff・fi・fl・ffi・ffl が制御文字 0x0B〜0x0F になったもの）だけを含む英単語も化けと数えません。本文が 50 文字未満のページ（数式だけのページなど）は判定しません。
  - 一部の文字化け：本文の 20% 以上が化けたページ（2 段組の片方だけなど）、または大半の語が化けた段落があるページ。化けた段落だけを原文のまま残し、残りは翻訳します。化けた段落がなく数式・表などが化けているだけのページは、原文との照合を促す文言で表示します。上下 10% の余白（配信スタンプやランニングヘッダー）は率に数えず、余白にある化けた段落と化けた文字が 10 字未満の小さな段落（アイコンフォントなど）は原文のまま残しますが一覧には出しません。手元の論文 11 本・約 380 ページでは正常なページの率は最大 0.3% でした。
  - 画像だけのページ：上下 10% の余白を除いた文字が 50 文字未満で、画像がページ面積の半分以上を覆うページ（スキャン。余白の配信スタンプやランニングヘッダーは数えません）。図だけのページでも 50 文字以上のキャプションがあれば対象外です。
  - 文字コードがずれただけで普通の英字に見える文字化け（例：`SURSRVHG`）は判定できません。日本語・中国語のフォントは英単語を含まないため数式フォントと推定されやすく、読める部分が本文の率に数えられません。そのため一部だけ化けた日本語・中国語のページは「一部」ではなくページ全体が要OCRになり、読める部分も翻訳されないことがあります。すべてのページに文字がないPDFは追加時に拒否します。
- レイアウト解析は PDF のテキストブロックに基づきます。複雑な図表・色付き背景・回転文字では意図しない重なりが起きる場合があります。
- 長い段落は分割して翻訳します。分割箇所をまたぐ文脈や数式の意味は、原文と照合してください。
- 解説とチャットは抽出テキストに基づき、図の画像そのものは AI へ送りません。
- 長い論文や複数論文へのチャットは、英語キーワード生成と文字列検索で選んだ既定10ページの抜粋を参照します。検索ページ数は20・30ページに増やせ、検索補助語と現在の論文の追加参照ページも指定できます。回答の参照リンクからページの原文抜粋を確認できます。意味検索や網羅性の保証はありません。
- 回答内の引用の文書 ID とページ範囲は検査しますが、解釈の正しさは原文で確認してください。

## レイアウト検証ツール

`tools/` には翻訳レイアウトを検証するための開発用スクリプトがあります。次の 2 つは通常の翻訳と同じ接続設定を使うため、モデルの利用枠を消費します（最後の抽出結果の比較は AI を呼び出しません）。

**新規翻訳による検証**：既存の `translated.pdf`・抽出情報・キャッシュを読まずに、選んだページを現在のコードで新規翻訳します。

```bash
uv run python -m tools.review_fresh_layout --papers <論文フォルダー> --output <新しい出力フォルダー> --seed 20260916 --count 3
```

出力には原文と訳文の PNG、対訳 PDF、`manifest.json` が含まれます。`--case 論文IDの先頭:ページ番号` で特定ページを指定できます（複数指定可）。既存の出力フォルダーへの上書きは拒否します。共通の文を含むページはまとめて生成します。

**検証結果のライブラリへの反映**：

```bash
uv run python -m tools.apply_layout_review --papers <論文フォルダー> --review <検証出力フォルダー> --case 論文IDの先頭:ページ番号
```

`--case` を省略すると、その検証で完了した全ページを反映します。変更前のファイルは論文フォルダー内の `review-backups` に保存し、論文ごとに反映済みの新しい 5 件を残します（それより古いものと、それより前の失敗した反映の作業フォルダーは削除します）。共通の文を含むページは同時に反映する必要があり、片方だけの差し替えは拒否します。反映中はアプリから同じ論文の翻訳を実行しないでください。

**抽出結果の比較**：レイアウト処理の変更前後で、全 PDF のブロック・書式判定・読み順・段落の継続・翻訳単位・ページごとの文字の増減を比べます。AI は呼び出さず、ライブラリは読むだけです。

```bash
git worktree add ../papeer-base <比較元のコミット>
uv run python -m tools.compare_layout snapshot output/layout/before --code ../papeer-base
uv run python -m tools.compare_layout snapshot output/layout/after
uv run python -m tools.compare_layout diff output/layout/before output/layout/after
```

`snapshot` の対象は既定で現在のライブラリの `papers/*/original.pdf` で、PDF ファイルや PDF のフォルダーも指定できます。出力先が指定したライブラリ（PDF だけを指定した場合はその論文のライブラリ、ライブラリ外の PDF はそのフォルダー）や既定のライブラリの中なら拒否します。`--code` は現在と同じパッケージ構成（`papeer.pdf.pdf_engine`）のチェックアウトに限ります。`diff` は文書ごとの差分の表を表示し、詳細を `output/layout/before-vs-after.json` に保存します。
