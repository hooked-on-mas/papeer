# 翻訳処理の仕様

PDF を日本語に翻訳し、原文と同じレイアウトの `translated.pdf` を生成する処理の挙動と制限をまとめます。実装は `papeer/translation/`、`papeer/layout/`、`papeer/pdf/`、`papeer/core/service.py` にあります。段・ページをまたぐ結合の詳細は [reading-flow.md](reading-flow.md) を参照してください。

## 基本の流れ

1. PyMuPDF でテキストブロックを抽出し、`document.json` に保存します。
2. ブロックを翻訳単位にまとめ、バッチごとに AI へ送ります。
3. 1 ページ分の訳文がそろうたびに、そのページのプレビューを生成してビューアへ反映します。
4. 完了時に `translated.pdf`、`translation.md`、`translation-report.json` を保存します。

原文と同じページ数を保ちます。長い訳文は元の枠内に収まるよう縮小します。全文を読む場合は `translation.md` も利用できます。

### 途中のファイルと交互 PDF

- ページのプレビューは論文フォルダーの `translation-pages/<実行ID>/` に作ります。翻訳が完了するとビューアは `translated.pdf` を表示するため、プレビューは削除し、置き換える前の `translation-cache.json` の控え（`previous-translation-cache.json`）だけを次の翻訳まで残します。
- 中止・エラーで終わった翻訳のプレビューは、表示と再開に使うため残します。`translation-preview.json` が指していない古いプレビューは、翻訳の終了時とアプリの起動時に削除します（起動時は同期で大量の変更にならないよう、完了済みの翻訳のプレビューには触れず、その論文の次の翻訳の終了時に整理します）。
- 原文と訳文の交互 PDF（`interleaved.pdf`、奇数ページが原文、偶数ページが訳文）は翻訳時には作らず、「原文・日本語訳（交互）を外部で開く」か書き出しのときに作ります。論文フォルダーに作ったものは、訳文が変わるまで再利用します。

## 読み順と段・ページをまたぐ本文

ページの列配置から読み順を復元し、文が続いている根拠のある隣接ブロックを結合して一度だけ翻訳します。訳文は句読点などで元の領域に配分します。

- ページを指定して翻訳した場合、同じ文を共有する関連ページも対象に含め、進捗とレポートに記録します。
- 見出し・独立数式・図表・参考文献をまたぐ曖昧な結合は行いません。
- 採用・見送りの判断は `document.json` の `continuations` と `continuation_decisions` で確認できます。
- 3 段以上や複雑な混在レイアウトは対応範囲外です。

## 数式

- **ブロック数式** は翻訳・描き直しをせず、元 PDF の描画を保持します。数式と本文が同じテキストブロックに含まれる場合も、配置を調べて分離します。
- **インライン数式** は元 PDF から高解像度で切り出し、訳文中に配置します。
- 数式の目印の欠落・変更・重複を検出した場合、正常なブロックを先に保存し、失敗したブロックだけを自動で再翻訳します。
  - 追加 1 回目は本文と数式番号を分けて受け取り、目印をアプリ側で復元します。
  - 追加 2・3 回目は数式の位置を固定して本文だけを翻訳します。
- 数式の検出には文字・フォントの使われ方・座標を使います。すべての PDF での完全な検出は保証できません。抽出文字からの TeX 再構成は行いません。

## 参考文献と表の保持

**参考文献**：References・Bibliography などの見出し以降を候補とします。次のいずれかを確認できたブロックだけ原文のまま保持します。

- 出版年
- 行頭の `[2]` 形式の番号
- 引用符で囲まれた題名
- 3 件以上の文献番号の連番（`1.`・`1)`・`1` 形式）
- DOI

ページをまたいでも判定を続け、Appendix などの見出しで候補範囲を終了します。判断が曖昧な文献は翻訳対象に残します。判定理由は `document.json` の `reference_evidence`、保持した ID は `translation-report.json` の `preserved_reference_blocks` で確認できます。

**表**：罫線付きの表と横罫線だけの表を検出し、セル内を翻訳対象から外して原文の配置・文字・罫線を保持します。表題と周囲の本文は翻訳します。罫線のない表は自動検出の対象外です。

## 再翻訳・再開・キャッシュ

専門用語辞書は全論文で共通です。翻訳ダイアログの「未登録語を確認して翻訳へ」で、AIが論文の原文から既存辞書にない専門用語のうち、訳語の判断が必要な語だけを日本語訳の案と一緒に抽出します。対象は、複数の訳語が使われている語、定訳がなく訳語・カタカナ・英語のままのいずれにするか決める必要がある語、一般語を特殊な意味で使っている語、通常の訳語では文脈上誤解を招く語です。Model Predictive Control（モデル予測制御）のように訳語が一つに決まる語は抽出しません。「新規」の候補と過去の登録語を同じ一覧で確認・検索・修正し、「辞書を適用して翻訳を開始」で追加内容を保存して翻訳します。「辞書を保存」だけでも登録できます。AIは既存の訳語を上書きせず、生成の失敗・中止時は辞書を変更しません。

共通辞書の「辞書をエクスポート」でJSONファイルを書き出し、「辞書を読み込み」で取り込めます。書き出しは検索・表示タブに関係なく、未保存の編集と候補を含む一覧全体です。読み込みは未登録語だけを追加候補にし、同じ原語（大文字・小文字を区別しない）は既存の訳語を保持します。異なる訳語の重複は比較表で確認でき、必要なら辞書一覧で修正できます。「辞書を保存」または翻訳開始までは共通辞書に反映されません。

ファイルはUTF-8のJSON（最大10MB）で、`{"format":"papeer-glossary","version":1,"terms":[{"source":"control","target":"制御"}]}` の形式です。旧形式の `[{"source":"control","target":"制御"}]` も読み込めます。原語・訳語は各100文字までで、不正な形式・空欄・ファイル内の原語重複がある場合は読み込み全体を拒否します。

辞書は `library.sqlite3` の `global_glossary` に保存され、フォルダーや論文による適用範囲の指定はありません。旧辞書は初回参照時に一度だけ統合します。同じ原語の競合はフォルダー名順、次に論文ID順で後の訳語を採用します。元のフォルダー辞書と `papers/<論文ID>/glossary.json` は移行元として残しますが、以後は翻訳に直接適用しません。共通辞書から削除した語が旧辞書から復活することはありません。

辞書の変更は、各論文で次に翻訳を実行した際、指定範囲のうち該当語を含むページに反映します。影響のないページはキャッシュを再利用します。保存済みPDFを一括で書き換える処理は行いません。別画面からの変更を上書きしないよう、古い一覧を使った保存は拒否します。AIによる訳語の遵守は完全には保証されないため、重要な用語は原文と照合してください。

「翻訳の確認・修正」で未翻訳・文字情報のないページ・小さな文字・生成失敗・スキップした段落を確認できます。翻訳済み段落の手動修正やAI修正案を比較して採用すると、関連ページのPDFとMarkdownを作り直します。数式の目印の欠落・重複は採用前に拒否します。修正履歴は `translation-revisions.json` に保存し、前の訳文に戻せます。原文の抽出結果または辞書が変わった段落は再翻訳してから修正してください。

- 完了した翻訳ブロックは `translation-cache.json` に保存し、中断・エラー・アプリ再起動の後も再利用します。
- 再翻訳は初回を除き 1 ブロック最大 3 回です。回数と実行済みの方式はリクエスト前に保存し、中断や再開でもリセットしません。
- 3 回で復旧できないブロックは原文を残してスキップし、翻訳レポートに記録します。
- 本文と数式の分離や訳文の配置に失敗したページはスキップして次のページへ進みます。失敗理由は `translation-report.json` に保存し、再実行時に PDF 生成を再試行します。
- 翻訳モデル・接続先を変えると、混在を避けるため翻訳キャッシュを作り直します。

## 翻訳キャッシュの識別値

保存済みの訳文は、AI が受け取る内容が同じ間だけ再利用します。キャッシュは次の組み合わせで区別します（`papeer/translation/translation.py` の `TranslationKey`）。

- ページの原文ユニット（抽出結果・数式の目印・ページのつながり・辞書の該当語）。ページごとに照合するので、変わったページだけを訳し直します。
- 使用中の翻訳プロンプト。既定の `translation.txt` は本文ではなく版番号 `BUILTIN_PROMPT_REVISION` で、設定画面で編集した独自のプロンプトは本文のハッシュで区別します（既定と同じ本文の上書きは既定として扱います）。
- 接続先とモデル。ベース URL は OpenAI 互換 API のときだけ含めます（CLI 接続では使わないため、PC ごとの設定値に左右されません）。
- 手動で上げる `TRANSLATION_PROTOCOL` と応答スキーマ

effort、依頼にだけ添える前後の文脈、復旧用プロンプト（`translation_recovery`・`translation_fallback`）は含めません。コードを変更しても自動では再翻訳しないため、依頼や検証の変更で既存の訳文を作り直すべきときは `TRANSLATION_PROTOCOL` を 1 つ上げてください。既定の `translation.txt` を直したときも同様で、訳し直すべき変更なら `BUILTIN_PROMPT_REVISION` を上げます。版番号を上げずに既定の文面を直すと、古い文面で訳した訳文がそのまま使われ続けます（文言の微修正で全論文を訳し直さないための割り切りです）。`tests/test_page_selection.py` が `translation.txt` の SHA-256 を固定しており、文面を変えるとこの判断を促して失敗します。レイアウト・PDF 生成だけの変更では、次に翻訳を実行したときに保存済みの訳文から PDF を作り直します（AI には送りません）。翻訳していないページや指定外のページの PDF はそのまま残ります。

識別値は `translation-cache.json` の `translation_version` と各ページの `version` に保存し、閲覧画面のツールバーに「翻訳時SHA」として先頭 7 文字を表示します。

### 以前の版のキャッシュ

以前の版はコードのハッシュ（`code-sha256-…`）で訳文を区別し、プロンプトと接続先は記録していませんでした。このキャッシュは、次の条件をすべて満たすページを AI に送らずにそのまま引き継ぎ、次の翻訳時に新しい識別値で保存し直します。

- ページの原文ユニットが一致する
- ページに記録されたモデルが現在のモデルと一致する（接続先は記録がないため照合しません）
- 使用中の翻訳プロンプトが既定の版 1（`builtin-1`）である。既定の文面を直しても版番号を上げていなければ版 1 のままです。識別値を導入した時点の既定の文面と同じ上書き（`LEGACY_PROMPT_SHA256`）も版 1 とみなします。独自のプロンプトに編集している場合は、どのプロンプトで訳したか分からないため訳し直します。
- `TRANSLATION_PROTOCOL` が 1 のまま

途中まで訳したページの訳文と再翻訳の回数記録も、プロンプトと `TRANSLATION_PROTOCOL` の条件に加えて、論文全体の原文ユニットと接続先・モデル・ベース URL が以前の版の最後の翻訳と同じなら引き継ぎます。コード識別値のないさらに古いキャッシュは、初回のみ再翻訳します。

## コード識別値（描画）

`papeer/core/code_version.py` の `RENDER_SOURCES`（抽出・レイアウト・PDF 生成の Python ソース）から計算する SHA-256 です。翻訳の再利用には使わず、翻訳レポートの `render_version` とステータスバーの表示に使います。

- `layout`・`pdf`・`translation`・`providers` のモジュールは、`RENDER_SOURCES` か `RENDER_EXCLUDED` のどちらかに必ず載せます（`tests/test_code_version.py` が検査します）。ファイルを新設・移動したときは一覧を更新してください。
- 改行コードだけの変更は識別値に影響しません。
- 開発時は起動時にソースから計算します。配布ビルドでは `just build-sidecar` が生成する `code-version.txt` を同梱し、sidecar をコピーした後に同梱ソース全体（`papeer`・`sidecar`・`sidecar.spec`・`pyproject.toml`・`uv.lock`）の内容ハッシュを `sidecar-sources.txt` に記録します。`just build-app` の前に `just check-sidecar` が、`code-version.txt` と `sidecar-sources.txt` が現在のソースと一致することを確かめます（内容で比べるので、git checkout でファイルの更新日時や改行コードが変わっただけでは失敗しません）。

## 制限事項

- 文字情報のある PDF 向けです。OCR は未実装です。画像のみのページは原文のまま保持します。
- レイアウト解析は PDF のテキストブロックに基づきます。複雑な図表・色付き背景・回転文字では意図しない重なりが起きる場合があります。
- 長い段落は分割して翻訳します。分割箇所をまたぐ文脈や数式の意味は、原文と照合してください。
- 解説とチャットは抽出テキストに基づき、図の画像そのものは AI へ送りません。
- 長い論文や複数論文へのチャットは、英語キーワード生成と文字列検索で選んだ既定10ページの抜粋を参照します。検索ページ数は20・30ページに増やせ、検索補助語と現在の論文の追加参照ページも指定できます。回答の参照リンクからページの原文抜粋を確認できます。意味検索や網羅性の保証はありません。
- 回答内の引用の文書 ID とページ範囲は検査しますが、解釈の正しさは原文で確認してください。

## レイアウト検証ツール

`tools/` には翻訳レイアウトを目視検証するための開発用スクリプトがあります。いずれも通常の翻訳と同じ接続設定を使うため、モデルの利用枠を消費します。

**新規翻訳による検証**：既存の `translated.pdf`・抽出情報・キャッシュを読まずに、選んだページを現在のコードで新規翻訳します。

```bash
uv run python -m tools.review_fresh_layout --papers <論文フォルダー> --output <新しい出力フォルダー> --seed 20260916 --count 3
```

出力には原文と訳文の PNG、対訳 PDF、`manifest.json` が含まれます。`--case 論文IDの先頭:ページ番号` で特定ページを指定できます（複数指定可）。既存の出力フォルダーへの上書きは拒否します。共通の文を含むページはまとめて生成します。

**検証結果のライブラリへの反映**：

```bash
uv run python -m tools.apply_layout_review --papers <論文フォルダー> --review <検証出力フォルダー> --case 論文IDの先頭:ページ番号
```

`--case` を省略すると、その検証で完了した全ページを反映します。変更前のファイルは論文フォルダー内の `review-backups` に保存し、論文ごとに反映済みの新しい 5 件を残します（それより古いものと、それより前の失敗した反映の作業フォルダーは削除します）。共通の文を含むページは同時に反映する必要があり、片方だけの差し替えは拒否します。反映中はアプリから同じ論文の翻訳を実行しないでください。
