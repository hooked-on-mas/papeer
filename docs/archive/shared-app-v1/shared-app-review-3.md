## 2. 指摘と採用した修正

| ID | 優先度 | 反例 | 採用した修正 | 反映先 |
| --- | --- | --- | --- | --- |
| RV26 | P1 | Aがowner/子noteを削除し、未受信のBが子noteを編集。Library削除と内容DAGが別のため、新編集が隠れる/孤立/自動復活する | Library全体を1 metadata DAGへ固定。論理削除集合と観測headsを記録し、内容を保持。未観測の後着編集を削除項目の回復一覧へ露出。復元は逆Library batch | 設計8.1/8.3/9.3.2、M1/M5、F33/F38/R26 |
| RV27 | P2 | 原文Oを維持して訳文A→Bへ更新すると、Aの文字draft/gestureを残したまま背景だけ差し替えられる | surfaceのpage/背景/resource版変更も編集対象遷移とする。候補mappingを保留し、旧gesture取消・旧対象draft/未耐久guard後にbindingを一括更新 | 設計5/6.1、M3、F17/R27 |
| RV28 | P2 | 横端PDFの本文長押し後、選択handleを72px以上水平移動するとswipeと誤判定してpageが変わる | 本文選択/handleを共通入力ownerに追加。選択開始でpan/swipe候補取消、二指移譲/解除後も同gestureをswipeへ再利用しない | 設計6.3、M2/M3、F20/R28 |
| RV29 | P2 | PC/Webの処理を別々の独立sessionへ移しても、同じ挙動試験と禁止import検査だけなら合格できる | featureの権威となる共通entryを登録し、両本番compositionのmodule graphと受入操作の実行traceを検証。port内の操作意味の再実装も撤去確認 | 設計10、M0/M2〜M6、R29、受入記録6.4 |

RV26では、Library削除を文書内page削除と区別した。「内容も削除」は子noteもcatalog上の論理削除集合へ含める意味とし、物理消去をしない。内容/履歴は保持し、削除後も同期・列挙対象に残す。後着編集を表示する回復一覧は通常一覧と独立させ、Undo/復元時に新しい本文/annotationを古いsnapshotで上書きしない。Library全体が一つのDAGになるため、無関係のmetadata編集同士も競合し得る代償を明記した。全アプリ共通DAG・分散transactionは導入しない。

RV27/RV28はidentityの追加だけでは防げない、表示対象と入力ownerの切替規則の補完である。RV29は挙動の一致と実装の共有を別々に確認し、巨大な重複コード検出基盤を要求するものではない。
